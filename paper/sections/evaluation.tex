\section{Evaluation Design}
\label{sec:evaluation}
The broader evaluation will test whether the case-study mechanisms transfer
across programs and predicate families. The protocol fixes program groups,
variants, input cases, expected outcomes, and resource accounting before
aggregating results. Case studies in Section~\ref{sec:case-studies} are the
current evidence; the following comparisons are the study design.

\paragraph{Baseline versions and reproducibility.}
For each new experimental batch, CN verification and Fulminate instrumentation
will use the same build of the latest commit on the official CN default branch,
frozen with its dependencies for the entire batch. On 2026-10-17, the upstream
head was \href{https://github.com/rems-project/cn/commit/b4a2f009234d9c80380dbf95a9b2325e36a4705d}{\texttt{b4a2f00923}};
this identifies the next baseline, not a completed measurement.
We will archive full revision and dependency identifiers, executable hashes,
build settings, compiler and runtime-check flags, and exact commands.
Historical measurements retain their original versions; each claimed case and
its controls will be rerun before contributing to the new comparison.

\paragraph{Program groups and comparison units.}
Each group has a primary program and several implementation or specification
variants, with multiple inputs per variant. Existing source variants are
retained. Expected behavior is reviewed independently of a tool verdict,
including whether a case exercises defined execution, a functional mismatch,
a spatial mismatch, or an unsafe operation. Only the primary program requires
full verification. Every selected variant/input pair is a test unit.
Mutants from one program are correlated observations, so aggregate analysis
will report both group-level coverage and per-input outcomes.

\paragraph{Comparators and research questions.}
Fulminate~\cite{banerjee2025fulminate} is the direct runtime-checking baseline on matched CN contracts and
inputs. On the shared latest-version build, we will compare the standard
runtime-check configuration with a sanitizer-augmented configuration for
arithmetic and memory-safety cases.
Original quantified contracts and proved executable reformulations are
reported separately. COINS~\cite{yang2026coins} is compared on the shared pure input/output relation under the same
model and proof budget. A proved admission is positive evidence;
an unproved rejection remains an unconfirmed prediction. This comparison
isolates what execution-derived state and
internal observations add. Gillian-C~\cite{santos2020gillian,maksimovic2021gillian} supplies
an independent symbolic-testing comparison on a reviewed common feature
subset. Unsupported inputs remain visible in coverage figures.

CN and \qcp{} verify each primary program's original contract once, without
adding test-input equalities. This comparison asks how early instance
feedback and its cost relate to full verification; their denominators are
kept separate. Within each execution strategy, the four combinations of spatial SMT on/off
and ITP on/off measure automatic decision coverage and the contribution of
proof completion. Strategy pairs use identical bindings and observation
schedules. We report body-execution and summary-model outcomes separately,
with verified primaries serving as agreement controls and insufficient
summaries as interface-diagnosis controls.
The protocol asks: which violations are detected, which original assertions
can be checked, which obligations require proofs, and what each completed
decision costs?

\paragraph{Outcomes and cost accounting.}
Reports retain pass, confirmed violation, unresolved, expected semantic
execution error, unsupported input, and infrastructure error. Following the distinction between noncompliance and prover incapacity
in proof-failure diagnosis~\cite{petiot2018stady}, a proof timeout never
counts as detection. For proof-producing routes, the report additionally
records goal coverage, kernel replay, and admitted assumptions.

Each group receives a result-and-cost table. CN records verification time and
peak RSS; Fulminate records instrumentation/compilation and test execution
separately. \qcp{} and \tespec{} separate VC generation/execution, agent proof
filling, proof compilation with assumption audit, and independent kernel
checking. One execution's complete residual VC set is one ITP job, including
retries. Agent comparisons use \texttt{gpt-6.1-sol} with fixed budgets and
record input, output, and total tokens. Peak RSS is measured per stage with
its process-scope definition; memory peaks are not summed. Repeated isolated
runs will report average per-execution cost, retaining raw records and failed
attempts. Reused proofs are identified so replay cost is not mistaken for
fresh proof-generation cost.
