\section{Introduction}
\label{sec:introduction}
Fixing a program's input does not necessarily make its specification
executable. Consider a routine that returns the least nonnegative integer
whose square is at least 13. The result is 4, but its contract may
characterize leastness by relating that result to \emph{every} nonnegative
integer. The computation is finite; the resulting assertion still
quantifies over an unbounded domain. For stateful C programs, the contract
must also describe the memory that the routine reads, modifies, and owns.

Separation logic expresses these functional and spatial requirements in
a common language~\cite{reynolds2002separation}, as used by CN and
VeriFast~\cite{pulte2023cn,jacobs2011verifast}. Fulminate brings executable CN contracts to
runtime testing~\cite{banerjee2025fulminate}. Proof-oriented specifications
also contain mathematical relations whose computational interpretation is
less direct. Some admit a finite monitor, but discovering that monitor
and establishing its equivalence requires additional specification work.
A programmer can therefore write a precise contract and run a concrete
example, yet still lack an oracle for checking it against the contract
as written~\cite{barr2015oracle}.

We present \tespec{}, a method for \emph{proof-based testing of
separation-logic specifications for C}. Its central idea is to use
execution to determine program states and proof to check the specification
at those states. Input bindings restrict the initial domain. Symbolic
execution follows available function bodies and loop iterations, retaining
the values and memory resources they produce. Selected annotations become
propositions in the original verification logic. Automatic reasoning
discharges supported obligations; remaining propositions become
proof-assistant tasks.

Realizing this idea requires separating an observation from the execution
it observes. A verifier may replace a loop by its invariant or a function
body by its summary~\cite{dardinier2023inlining}. When that annotation is itself under test, replacement
can discard the information needed to check it.
\tespec{} instead generates obligations on copies of the reached state.
For a state assertion $P$ and a fully resolved check $Q_A$, it records
$P\vdash Q_A$ while retaining $P$ for the continuation.
Changing an intermediate assertion changes the question asked of the
state; subsequent computation continues from the same state.
Section~\ref{sec:example} illustrates this mechanism with the least-root
routine.

The construction preserves the relation between heap cells and their live
values during simplification and accounts explicitly for local storage
at observation boundaries. The oracle combines VC evidence with entry
feasibility and execution coverage. Acceptance concerns the domain selected
by the bindings, which may retain symbolic addresses or other unbound
inputs. Full \qcp{} verification addresses the original contract over all
admissible inputs. These workflows share specifications and proof
infrastructure while answering different development questions.

Recorded case studies examine the mechanism from three directions.
For a negating read at \texttt{INT\_MIN}, \tespec{} rejects an arithmetic
safety obligation while the recorded Fulminate configuration exits
successfully. For least-root and divisibility, proof completion checks
original quantified contracts; proved finite reformulations provide
runtime controls. Ownership examples examine how automatic spatial
reasoning and checked refutations resolve residual obligations.
Section~\ref{sec:case-studies} presents their sources, inputs, and evidence.

Our contributions are:
\begin{enumerate}
\item \textbf{Execution with copied observations.}
We construct obligations at function, loop, and intermediate boundaries
while retaining the program's evolving state
(Section~\ref{sec:approach}).
\item \textbf{A formal account of instance checking.}
We give construction rules, oracle interfaces, and verdict judgments,
with trace-preservation and acceptance arguments supported by a mechanized
reference model (Section~\ref{sec:semantics}).
\item \textbf{An implementation and comparative evidence.}
We implement the method using \qcp{}'s symbolic execution and Rocq
obligations, provide controlled case studies, and specify the broader
evaluation and cost protocol
(Sections~\ref{sec:case-studies} and~\ref{sec:evaluation}).
\end{enumerate}
