# teSpec：保持执行状态的规约测试

本文定义 `inline-preserve/v1` 的实例化、持续求值、循环执行、函数调用与检查边界。实现复用 sac/QCP 的符号执行器及 VC 生成器，teSpec 通过二进制接口调用。先前的 `P×I` 状态与中间放缩方案保存在 `superseded-instance-state/`，不属于本文算法。

## 1. 测试的语义对象

具体 C 状态为 σ=(ρ,h)，逻辑解释为 η。空间断言按 QCP 内存模型解释；`*` 是分离合取，普通逻辑合取共享同一个堆。函数契约为 `{R(a₀,w)} f(a) {E(a₀,w,r)}`，其中 a₀ 为入口参数值，w 为 With 逻辑参数，r 为返回值。

测试绑定 θ₀ 是有类型、按逻辑变量 ID 定义的部分替换。指针地址可以保持符号化；内存内容、长度和递归数据的构造项可以被绑定。绑定不可变入口逻辑值不妨碍 C 参数及其所指内存被程序修改。

两个目标严格区分：

- 初始存在性：`SAT₀ ≡ ∃η,ρ,h. R[θ₀](ρ,h,η)`。
- 执行正确性：对所有满足 `R[θ₀]` 的初始状态，已完成执行的安全性和返回状态满足所选义务。

Require 的一个 SAT 模型不会自动变成程序输入。剩余符号在执行正确性中仍表示所有允许的解释。例如只绑定链表长度 2，节点地址仍符号化，节点内容若未绑定也仍符号化。

## 2. 单一逻辑状态与模式

配置为 `C=⟨pc,P,K,θ₀,Ω,b,m⟩`。P 是 QCP Assertion（纯约束、程序变量到地址的映射、空间谓词及量词）；K 是调用栈，Ω 是检查义务，b 为执行预算，m 为检查策略。实现不维护另一份可变实例状态。

| 检查模式 | 循环与有函数体的调用 | 中间检查 |
|---|---|---|
| `entry-exit` | 实际迭代、实际内联 | 默认忽略；可显式启用 `check-preserve` |
| `all-boundaries` | 相同的实际迭代与内联 | 启用 `assert/inv/Require/Ensure` 检查 |

旧名称 `expand` / `no-expand` 保留为输入别名。`all-boundaries` 表示检查所有经过的边界。两个模式均检查入口 Require、程序安全性及顶层 Ensure。安全性 VC 不受中间检查开关控制。

只有 C 的转移规则与语义保持的化简能改变 P。注解检查满足：

`Boundary(P,A,Ω) = (P, Ω ∪ {copy(P) ⊢ Resolve(A)})`。

返回的 P 是原状态。即使 VC 不成立或尚未解决，仍从原状态继续执行。普通程序分支可以添加其真实路径条件；不能把未经证明的 Assert、Inv 或 Ensure 作为路径条件。

## 3. 实例化及持续求值

`Subθ(F)` 是类型正确、避免捕获的逻辑替换。进入函数或局部量词前先 α-重命名。被替换变量的绑定项应先移除，再替换自由出现位置，避免把替换后的已有符号错误地重新量化。

共享化简模块 N 的规范为：

`Γ ⊨ F ↔ ∃z. NΓ(F)`，

z 是定义展开引入的新鲜变量；不引入变量时为空。Γ 只含当前分支可用的事实。N 求值已知算术、布尔、列表和可执行逻辑定义，展开可用的空间谓词定义；未知项和不能终止的展开保留为残余。递归谓词按实际参数和守卫展开，所有可行分支必须保留。

化简还必须保持断言与外部返回项的联合语义。定义 `Obs(F,t) = {(σ,v) | ∃η. σ,η ⊨ body(F) ∧ v=⟦t⟧η}`，其中 F 的存在变量由同一个 η 解释。若 t 不同步改写，必须满足 `Obs(N(F),t)=Obs(F,t)`。仅证明闭合断言 F 的等价性还不够：从 `∃r. r=2 ∧ cell(p,1)` 消去 r，却仍把 r 作为返回项，会丢失返回值约束。

实现对一次定义展开前已有的存在变量集合 B 保持绑定关系，只允许消去本次 α-重命名后新引入、且不在 B 中的局部见证。分支内常量传播保留作为依据的等式。这样返回项、表达式栈和调用帧引用的旧变量仍受原断言约束。回归包含直接返回等式、析取、存在返回见证、嵌套定义和错误后条件。

C 表达式求值仍复用 QCP 的有类型运算、内存读取和安全性义务。不能用数学整数化简掩盖溢出、除零、未初始化读取或非法移位。空间折叠和展开需保持当前堆的解释，不能仅凭同名谓词选用一个特殊实现。

每次真实执行转移：

`(P₁,…,Pₖ; Ωe) = QCP.Exec(c,N(P))`，

`Successors = {N(P₁),…,N(Pₖ)}`，并累积 Ωe。没有依据证明不可达的分支不得丢弃。跟踪输出是 P 的观察，不参与执行。

## 4. 实际函数调用算法

### 4.1 实参求值与调用身份

对调用 `x=f(e₁,…,eₙ)`，首先用 QCP 的表达式求值器求函数目标及全部实参。每条求值结果携带其自己的状态 `Pj`、值元组 `vj` 和安全性 VC。每个 `(Pj,vj)` 独立进入调用；传递求值后的项，不在函数体写内存后重新读取参数表达式。

函数体按前端函数身份查找。确定的函数目标使用其已登记的 PSTree。不能确认目标、缺少函数体或无法实现的调用形式返回未完成状态。声明和定义的关联使用函数 ID，不能按程序文件名或样例名分派。

### 4.2 生成调用边界的检查目标

启用检查时，在 `copy(Pj)` 上调用 QCP 的 `FuncCallExec(...,BOUNDARY_CALL)`：

1. 复用 QCP 的契约选择、类型参数、`where` 填充、参数替换及 α-重命名。
2. 用正常分离逻辑匹配器寻找同一组入口 With 绑定 ω 和剩余堆 F。
3. 生成 QCP 原有的 Require/frame 义务：`Pj ⊢ R[vj/a₀,ω/w] * F`。
4. 保存候选返回目标 `Gj = E[vj/a₀,ω/w,r] * F` 及其返回项、存在量词和 VC。候选只用于检查。

With 在调用入口确定。Ensure 不能另选一组与 Require 无关的 With 见证。后条件自己的存在量词允许在每条返回路径上选择见证。没有匹配结果时记录 `contract_binding_unknown`，不得默认为匹配成功。当前部分 With/type 填充失败会提前终止该次运行并报告 UNKNOWN；后续工作可将这类失败也隔离为独立残余检查。

`BOUNDARY_CALL` 保留返回目标与返回项的关联，禁止在加入实际返回值等式前消去后条件中的返回变量。它复用正常调用的匹配和 VC 构造，但不把其结果作为执行后继。

### 4.3 新鲜调用帧

为本次调用分配新帧 κ。帧记录恢复点、调用前程序变量地址映射、被遮蔽的局部变量、控制流状态，以及检查所用的不可变入口逻辑参数。

每个标量或指针形参 ai 获得新鲜地址 αᵢ：

`Pentry = Pj * (α₁ ↦τ₁ v₁) * … * (αₙ ↦τₙ vₙ)`。

程序变量 ID 在前端可复用，但 `Localκ(ai)=αᵢ` 随调用新鲜化。指针值 vi 保持原身份：两个实参相等时，被调函数观察到相同地址；新分配的是保存指针的形参槽，而非指针指向的堆。

结构体按值形参调用 QCP 的记录复制规则，在新的形参存储上复制字段和未初始化状态。结构体的指针字段复制地址值，因此仍与原堆共享别名。记录复制若产生当前适配器无法保留的多分支结果，报告 UNKNOWN。按值 union 参数尚未支持。

函数体和递归调用都从 `Pentry` 实际执行。PSTree 的运行状态、循环计数器、返回/跳转槽按调用复制并重新关联。局部声明创建新鲜存储；递归重用源程序变量 ID 时暂存并移除上一层映射，返回后恢复。

### 4.4 函数体内部注解

每次访问注解都克隆其语法树，使用当前路径状态生成目标。这样不会重用上一次访问时解析出的常量、地址或中间断言。

注解里的程序变量通过当前调用的 `Local` 映射解析。With 变量通过本次调用的不可变 ω 替换。函数局部断言的检查目标带上该调用的 QCP 剩余堆 F。所有替换和补 frame 只发生在检查目标上。

重复调用、递归和循环中的检查分别生成 VC。若当前状态为析取，对每条源状态分别解析和检查，避免把一个分支的值带入另一个分支。`which implies` 保留其逻辑蕴含义务，证明结果不改写执行状态。

### 4.5 返回与清理

每个实际 `return e` 使用 QCP 返回表达式求值，得到 `(Pk,rk)`。必须保留所有可行返回分支，包括提前返回和条件分支。非 void 函数完成后没有返回值时报告 `missing_return_value`，不合成任意值。

按真实词法作用域释放该帧局部存储；再按该调用新鲜形参地址清理形参存储，复用 QCP 的类型相关释放规则。只清理当前帧所拥有的存储，保留共享堆写入。结构体返回使用 QCP 的返回临时记录，在被调函数局部生命周期结束后供调用者复制。

恢复调用者的地址映射、环境和控制流位置。得到 `Pk⁻` 后，启用检查时对每条实际返回生成：

`Pk⁻ ⊢ ⋁j ∃uj. (Ej[vj/a₀,ω/w,rj] * Fj) ∧ (rj=rk)`。

无返回项约束的 void/忽略返回值契约省略等式。若目标有多个后条件分支，保留完整析取。直接添加等式比假定返回项总是一个变量更一般，既支持常量返回条件也支持存在返回见证。

最后把 `(Pk⁻,rk)` 推回调用者表达式栈。候选 Ensure、匹配 frame 和检查结果均不替换 `Pk⁻`。

### 4.6 例子

```
void bump(int *p)
/*@ With v Require data_at(p,int,v)
    Ensure exists w, data_at(p,int,w) */
{ *p = *p + 1; }
```

调用前 `P = data_at(P₀,int,3) * data_at(Q₀,int,8)`，调用 `bump(P₀)`。入口匹配给出 `v=3` 与 `F=data_at(Q₀,int,8)`。新形参槽 α 保存 P₀；写入通过 P₀ 修改共享单元，得到内容 4。清理 α 后实际状态为 `data_at(P₀,int,4) * data_at(Q₀,int,8)`。弱 Ensure 的 VC 可取 `w=4`，但执行状态中的 4 不被存在量词取代。

## 5. 循环算法

每次到达注解位置，在启用检查时生成 `Pt ⊢ Inv`；随后继续使用 Pt 求值实际循环条件。真分支执行循环体，假分支进入出口。`continue` 到对应继续位置，`break` 到对应出口，提前 `return` 保留其实际返回路径。`for` 的更新表达式与 `do-while` 的条件位置遵循 QCP 控制流。

不以 Inv 代替 Pt，不构造任意的归纳头状态，也不从 Inv 假设循环退出状态。这里验证的是测试输入所允许的实际访问状态，不是一次证明覆盖任意输入的循环归纳定理。

预算 b 对两个模式均生效。达到循环、递归或外部超时限制后，结果为 UNKNOWN，并保留资源信息；不能把有限前缀当作执行完成或不终止证明。

## 6. Require 可满足性与结果

入口实例化和归一化之后调用原有前条件检查流程。SMT/专用可验证规则仅对其编码完整的片段报告 SAT；检测到冲突绑定、相同地址上的分离存储、数组重叠、类型取值范围矛盾等可报告 UNSAT。抽象递归空间谓词、布局和其他未解决内容保留存在性 VC。不能把任意空间谓词默认当作可满足。

该自动阶段不启动证明 Agent。VC 生成和文件产物保留给外部固定检查流程；没有检查证书时报告 `certificate=NOT_CHECKED`。本文实现和回归并不等价于对整个 QCP/SMT/C 实现的机器检验证明。

PASS 要求：初始 Require 已判定 SAT，所有可行路径执行完成，所选安全性、最终 Ensure 和中间 VC 已关闭，且没有预算、缺少函数体或不支持行为。INVALID 表示入口 Require 不可满足。UNKNOWN 表示未决 VC 或执行不完整。ERROR 单独表示解析/执行器无法处理的错误；这类结果不能计作通过。

声明-only 的测试目标可仅检查 Require，scope 为 `specification-only`，执行及 Ensure 为 NOT_RUN。实际执行中遇到只有契约的外部调用则 UNKNOWN；没有函数体且没有契约时报错。

## 7. 相对健全性命题

假设 QCP 所支持 C 子集的基本转移、内存/布局规则与 VC 规则健全，N 满足上述语义保持条件，求解器认可的义务有效，且整个执行中没有未报告的路径丢失。对于执行 scope 的 PASS，有：

`∀σ₀∈⟦R[θ₀]⟧. Exec(body,σ₀)` 的每个执行由已完成的符号路径覆盖；其程序操作安全，终止状态满足 `E[θ₀]`，并满足所启用的每个访问边界。

论证按转移及调用栈深度归纳：入口由实例化定义成立；基本语句由 QCP 健全性保持覆盖；化简由等价性保持覆盖；分支保留所有可行后继；边界返回相同 P，因此既不增加执行假设也不删除路径；调用分配新鲜帧并共享指针所指堆，实际函数体执行由归纳假设覆盖，类型相关清理及映射恢复给出调用者后继；返回蕴含 VC 推出 Ensure。循环通过逐次转移展开，预算耗尽不满足 PASS 条件。

这是明确列出依赖条件的算法健全性论证。实现的测试证据另见 `instance-semantics-evaluation.json`；尚未完成独立的 Coq 元理论证明。

## 8. 实现对应与覆盖策略

| 算法部分 | sac/QCP 实现 |
|---|---|
| 实参求值、多分支、表达式返回栈 | `SymExec/SymExec/ExprExec.c` 的原有表达式执行路径 |
| 函数身份、调用树复制、新鲜参数、返回恢复 | `SymExec/SymExec/ConcreteCall.c` |
| With、frame、Require VC | `FuncCallExec` 的 `BOUNDARY_CALL`，复用原匹配器及 `FuncCallWit` |
| 实际返回对应 Ensure | `CheckInlineReturn`，复用 `CheckEntailment` |
| 结构体值复制及注解副本 | `SymExec/middle_end/SymExecutor.c` |
| 实际循环与控制流 | `SymExec/SymExec/StateMachine.c` |
| 共享求值与逻辑定义展开 | `SymExec/Utility/ExpressionNormalize.c`、`ExpressionPredicate.c` |
| 初始 SAT/UNSAT/UNKNOWN | `SymExec/SymExec/PreconditionCheck.c` |
| 不可变入口绑定 | `InstanceContext.c`；没有每个断言上的 I 缓存 |
| 模式、资源、文件产物 | sac JSON 与 teSpec 二进制控制器 |

覆盖评估同时保留三类证据：带预期的正反例回归；QCP 原始示例的定向绑定；整个 `QCP_examples` 的合成输入扫描。合成输入可能本就不满足 Require，不能把 INVALID 算作工具缺陷，也不能把扫描结果算作正确性 oracle。失败按语言/逻辑特征分类，不按函数名、文件路径或样例名添加特判。

## 9. 分类端到端验证

`benchmark/executor_e2e/cases.py` 描述 52 个功能程序和 37 个专项场景，覆盖控制流、整数语义、循环/递归、调用、数组/字符串、指针别名、结构体、链表、树/DAG、分配器模式、逻辑谓词、检查边界、Require、内存安全、预算及声明，共 18 类。

每个功能程序使用 4 组输入、原程序/错误后条件/程序变异三个版本，以及两种模式，共 1,248 次运行；专项场景增加 74 次。预期值由 Python 独立计算并与原生 C 的返回值、堆内容和指针关系交叉检查。每个程序变异必须由至少一组原生输入区分。运行器经公开 CLI 检查完整流程、VC 文件、哈希和资源报告。

当前 1,322/1,322 次运行符合预期，其中 779 次为负例检查，错误接受为 0。返回结果分布为 541 PASS、757 UNKNOWN、14 ERROR、10 INVALID；UNKNOWN 中包含故意错误的后条件及不支持情形。ASan/UBSan 下相同矩阵也全部符合预期，关闭了泄漏检查。测试中曾发现 8 次由返回绑定被消去引起的错误 PASS；第 3 节的绑定保护修复后，这些用例保留返回 VC。完整证据见 `executor-e2e-results.json`，本次未进行 ITP 证书重放。

测试方法参考用户提供的 Code-Specify-Test-Debug-Prove 论文 §4.3–4.5 对部分规约、错误所有权、错误条件、边界偏差及分配器输入的评估（[论文](https://doi.org/10.1145/3808278)，[官方产物](https://zenodo.org/records/19577402)）。本矩阵为独立程序，原生 oracle 覆盖所选有限实例；抽象递归谓词及真实动态分配器的覆盖由 QCP 语料扫描另行报告。
